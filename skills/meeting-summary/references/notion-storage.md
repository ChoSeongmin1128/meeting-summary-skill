# Notion 저장 방식 선택

회의록 저장에서는 접근 수단과 변경 범위를 나눠 선택한다. CLI, MCP, 커넥터라는 이름보다 현재 연결이 지원하는 읽기·쓰기 기능, 입력 크기, 정확한 부분 수정 가능 여부가 중요하다. 커넥터가 MCP 도구로 제공될 수도 있으므로 이를 항상 별개의 구현으로 가정하지 않는다.

## 1. 작업에 맞는 변경 범위

| 요청 | 기본 동작 | 적용 범위 |
|---|---|---|
| 페이지 하단에 요약본 또는 비교용 버전 추가 | `update_content` | 마지막 고유한 부분을 찾아 기존 내용 뒤에 새 요약 토글을 붙임 |
| 기존 요약이나 특정 안건 수정 | `update_content` | 해당 버전이나 안건만 정확히 찾아 교체 |
| 본문 전체 재구성 | `replace_content` | 사용자가 요청한 전체 본문을 교체 |

- 하단 추가에서 `old_str`는 실제 최신 본문의 마지막 부분 중 한 곳에만 등장하는 범위를 사용한다. `new_str`는 그 범위를 그대로 보존한 내용에 새 토글을 이어 붙인다.
- 기존 마지막 블록의 경계를 포함해 새 토글이 기존 토글이나 목록의 자식으로 들어가지 않게 한다. 반복되는 `</details>`만으로 위치를 찾지 않는다.
- 기존 버전 수정은 가능한 한 작은 고유 범위를 선택한다. 여러 곳과 일치하거나 일치하지 않으면 다시 읽어 대상을 확인하며, 이를 해결하려고 전체 페이지 교체로 자동 전환하지 않는다.
- 빈 페이지처럼 일치시킬 기존 내용이 없다면 지원되는 추가 동작을 사용한다. 페이지가 실제로 비어 있는 것을 확인했다면 `replace_content`로 첫 내용을 넣을 수도 있다.
- `insert_content`는 제공된 스키마에서 지원되는 경우 명시적인 하단 추가에 사용할 수 있다. REST API 문서에서는 legacy 동작이므로 기본은 `update_content`로 두고, 연결마다 지원 상태를 확인한다.
- 읽히지 않는 블록이 있으면 해당 내용을 삭제하거나 재구성하지 않는다. 읽을 수 있는 대상에 한정한 추가·부분 수정은 가능하지만, 불완전한 본문으로 전체 교체하지 않는다.

## 2. 접근 수단 선택

| 수단 | 사용 기준 | 확인할 점 |
|---|---|---|
| 연결된 Notion MCP / 커넥터 | Markdown 읽기와 부분 수정이 지원되면 우선 사용 | 현재 도구 스키마, 사용 권한, 입력 크기, 경고 및 비동기 완료 확인 |
| `ntn api` CLI | MCP가 없거나 기능·입력 제한 때문에 적합하지 않을 때, 큰 요청 JSON을 파일로 다루는 것이 유리할 때 | 현재 CLI 도움말과 API 스키마, 기존 로그인, 목적지 페이지 |
| 직접 REST API / SDK | 위 수단이 없고 기존 승인된 자격과 지원 라이브러리로 같은 Markdown 작업을 수행할 수 있을 때 | 현재 API 버전과 요청 형식, 자격정보 비노출 |
| 블록 API를 제공하는 도구 | Markdown 부분 수정이 없거나 필요한 블록 형식을 지원하지 않을 때 | 새 블록·대상 블록만 처리하고, 토글 자식과 분할 요청의 완전성을 확인 |
| UI 조작 | 적합한 연결 도구와 API를 사용할 수 없는 경우의 마지막 수단 | 목적지와 실제 저장 결과, 요약 내용·중첩 구조의 누락 여부 |

- 모든 환경에 같은 MCP 이름이나 기능이 있다고 가정하지 않는다. 실행 중인 Claude 또는 Codex 세션에 실제로 제공되는 도구 설명을 읽는다.
- 같은 작업을 수행할 수 있으면 준비된 연결 도구를 사용한다. 입력 제한과 반복되는 전체 본문 응답의 크기도 고려하며, 수단을 바꿀 때는 대상 페이지와 수정할 본문이 일치하는지 다시 확인한다.
- MCP 인증이 CLI로 공유된다고 가정하지 않는다. 기존 연결로 할 수 있는 작업을 위해 전역 로그인, 토큰, 도구 설정을 임의로 바꾸지 않는다.
- 이 스킬을 실행했다는 이유로 별도의 설치, 새 연결 생성, 다른 앱으로의 메시지 발송까지 허용된 것으로 보지 않는다.

## 3. MCP / 커넥터

- Markdown 명세는 해당 연결이 제공하는 문서나 리소스로 확인한다. 사람 이름은 작성 기준과 사용자 요청에 맞춘 표기를 저장 시에도 유지한다.
- `notion-update-page` 계열의 부분 수정 예시는 `command: "update_content"`와 최상위 `content_updates` 배열을 사용한다. 정확한 필드 이름은 현재 도구 스키마를 따른다.
- REST 요청의 `type` 및 중첩된 `update_content` 객체를 MCP 인자로 그대로 넘기지 않는다. 도구별 요청 형식과 API의 요청 형식을 구분한다.
- 비동기 작업이 반환되면 해당 연결이 제공하는 상태 조회 도구로 완료를 확인한다. 수락되거나 큐에 들어간 상태를 저장 성공으로 보고하지 않는다.
- 파서 경고가 있으면 무시된 내용과 자동 수정 내용을 확인하고 저장된 본문을 다시 읽는다.

## 4. CLI / 직접 Markdown API

- CLI로 본문을 바꿀 때는 `ntn api "v1/pages/<ID>/markdown" -X PATCH`를 사용한다. JSON은 파일로 준비해 stdin으로 전달한다.
- 부분 수정 요청은 최상위 `type: "update_content"`와 `update_content.content_updates`를 사용한다. 각 항목의 `old_str`와 `new_str`에는 정확한 원문과 교체문을 넣는다.
- 전체 교체 요청은 `type: "replace_content"`와 `replace_content.new_str`를 사용한다. 부분 추가·수정 작업에 전체 본문을 다시 보내는 방식은 기본으로 쓰지 않는다.
- 현재 CLI의 `ntn pages edit --content`와 그 별칭 `ntn pages update --content`는 전체 교체 입력이다. 하단 추가나 부분 수정에 사용하지 않는다. CLI의 `--content` 옵션과 Markdown API의 `update_content`를 같은 기능으로 취급하지 않는다.
- CLI의 동작은 현재 도움말과 구현·응답으로 확인한 기능을 기준으로 판단한다.
- SDK나 직접 HTTP 요청에서도 동일한 부분 수정 원칙을 적용한다. 도구별 스키마, API의 지원 버전과 비동기 응답 처리 방식은 현재 문서로 확인한다.

## 5. 보존 및 저장 확인

- 수정 직전에 최신 본문을 읽고, 준비한 수정 대상과 재대조한다. 페이지 전체를 덮어써 다른 편집을 되돌리지 않는다.
- 기존 표, 하위 페이지·DB, 원본 전사, 요청하지 않은 요약 버전을 보존한다. 보호 오류를 해결하기 위해 `allow_deleting_content`를 자동으로 켜지 않는다.
- 토글 내부 항목이 실제 자식 블록이 되도록 들여쓴다. 표와 표는 빈 줄만으로 붙이지 않고 사이에 문단을 넣는다.
- 응답이 불분명하거나 중간에 끊기면 먼저 실제 저장 결과를 읽는다. 같은 토글이나 버전을 중복 추가하지 않는다.
- 저장 후 요청한 위치, 토글 경계, 요청한 구성과 순서, 이름 표기, 요청하지 않은 내용 보존과 작성한 요약의 저장 누락 여부를 확인한다.
- 서식의 자동 공백 정리와 내용 손실을 구분한다. 결과가 길면 로컬 파일로 보관하거나 검증에 필요한 범위만 출력한다.
- 실제 확인 범위를 보고한다. 문서·스키마 검토, 로컬 형식 검증, 실제 Notion 쓰기 검증을 구분하며 수행하지 않은 검증을 성공했다고 말하지 않는다.
