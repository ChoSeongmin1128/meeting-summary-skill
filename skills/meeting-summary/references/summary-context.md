# 회의록 요약 작성 컨텍스트

회의록은 참석자가 공유 내용과 결론을 빠르게 확인하고, 불참자도 논의의 배경과 판단 과정을 이해할 수 있도록 작성한다. 아래 규칙은 Claude와 Codex가 함께 참고하는 회의록 요약 기준이다.

## 1. 자료 확인

- 사용자가 제공한 원본 전사와 해당 회의 페이지를 읽는다. 이미 확인한 적이 있어도 페이지를 수정할 때는 최신 본문을 확인한다.
- 회의 페이지의 표, 메모, 기존 기록을 대조해 작업명, 담당자, 일정, 진행 상태를 확인한다. 서로 어긋나면 어떤 자료에서 확인한 내용인지 구분하고, 확정되지 않은 부분을 임의로 보완하지 않는다.
- 사용자가 지정한 참고 예시와 피드백이 있으면 먼저 읽는다. 예시의 구성을 참고하되 현재 회의의 내용이나 확정 여부를 바꾸지 않는다.
- 현재 요청의 형식과 범위가 이 문서보다 우선한다.

## 2. 구성

사용자가 구성을 지정하면 그 형식을 따른다. 별도 지정이 없으면 `공유 사항 → 논의 사항 → 결정 사항` 순서로 구성한다. 기본 구성에서는 별도의 TODO나 액션 아이템 구분을 추가하지 않고, 이번 회의에서 정한 후속 작업은 결정 사항에, 확인이 필요한 문제는 논의 사항에 넣는다.

### 공유 사항

- 진행 상황, 기존 계획, 전달받은 변경 사항을 항목마다 한 줄로 정리한다.
- 회의 전에 다른 자리에서 합의된 내용을 전달한 경우도 공유 사항으로 분류한다.
- 인지하면 되는 정보를 담고, 배경 설명이나 검토 과정은 붙이지 않는다.

### 논의 사항

- 안건별 소제목 아래 쟁점과 검토 내용을 정리한다. 불참자가 논의의 배경과 판단을 이해할 수 있도록 실제 나온 의견, 대안, 반론, 제약, 조건과 남은 확인을 담는다.
- 배경, 대안, 판단 이유, 남은 확인 등의 표시는 해당 안건에 필요한 만큼 사용한다. 모든 안건에 같은 설명 틀을 채우지 않는다.
- 회의 중 의견이 바뀌면 처음 제안과 최종 판단을 구분한다. 채택되지 않았거나 철회된 제안도 쟁점이나 판단을 이해하는 데 필요하면 경과와 함께 남긴다. 최종 결정처럼 쓰지 않는다.

### 결정 사항

- 이번 회의에서 합의한 결론이나 실행할 일을 항목마다 한 줄로 정리한다.
- 담당자와 기한이 정해졌다면 같은 줄에 포함한다.
- 제안, 추측, 확인 중인 내용은 결정으로 쓰지 않는다.
- 결정의 이유와 검토 과정은 논의 사항에 남기고, 여기에는 결론만 담는다.

## 3. 정보 보존과 압축

- 업무와 관련된 서로 다른 사실, 쟁점, 의견, 대안, 결정과 후속 작업을 보존한다. 짧게 언급됐거나 결론이 나지 않았다는 이유로 제외하지 않는다.
- 담당자, 일정, 수치, 적용 범위, 조건, 예외, 위험과 의존 관계를 유지한다. 제안과 합의, 목표와 완료, 보류와 취소를 구분한다.
- 같은 뜻의 반복 발언과 재설명은 하나로 합친다. 반복 중 새로 붙은 조건이나 예외는 함께 남긴다.
- 발언 순서와 말투는 정리하되, 의견이 바뀐 이유나 대안의 채택·보류·배제 이유가 업무 이해에 필요하면 남긴다.
- 한 항목에는 한 가지 요점을 담고 의미가 유지되는 짧은 문장으로 쓴다. 같은 배경이나 설명을 여러 구분에서 반복하지 않는다.
- 글자 수나 항목 수에 맞추기 위해 서로 다른 업무 정보를 생략하지 않는다. 분량은 보존해야 할 정보의 양에 따라 정한다.
- 작성 후 원문과 대조해 고유한 업무 정보의 누락과 확정 여부의 변형을 확인한다. 이 확인 과정이나 점검 목록은 요약본에 추가하지 않는다.

## 4. 잡담과 사담 제외 기준

- 업무의 진행, 논의, 결정, 후속 작업과 무관한 내용은 요약에서 제외한다. 인사, 농담, 개인적인 일상 이야기, 회의와 무관한 대화, 의미 없는 반복이 해당한다.
- 사담처럼 들리는 내용도 일정이나 업무 수행에 영향을 주면 필요한 부분만 남긴다. 예를 들어 건강검진이나 휴가 이야기는 누가 언제 부재하는지만 기록하고 불필요한 개인 사정은 생략한다.
- 길거나 두서없는 발언이라도 결정의 이유, 반론, 조건, 위험, 의존 관계를 담고 있으면 뜻을 정리해 보존한다.
- 말투나 분위기를 근거로 중요한 내용을 제외하지 않는다. 요약에서 빼도 업무 이해나 판단이 달라지지 않는지를 기준으로 삼는다.
- 확인할 담당자, 처리 기한, 추가 질문은 잡담과 섞여 나와도 남긴다.
- 이 기준은 요약본에 적용한다. 기존 원본 전사는 전사 오류와 잡담을 포함해 그대로 보존한다. 사용자가 별도로 요청한 경우에만 원본이나 정리 전사본을 편집한다.

## 5. 표현과 정확성

- 공유 사항과 결정 사항의 '한 줄'은 한 항목에 한 가지 요점만 담는다는 뜻이다. 긴 문장에 여러 요점을 몰아넣지 않고 하위 설명도 붙이지 않는다. 화면 너비에 따른 자동 줄바꿈은 무관하다.
- 제목, 불릿, 하위 불릿, 필요한 부분의 강조를 활용한다. 긴 문단에 여러 쟁점을 몰아넣지 않는다.
- 설명이 필요한 논의는 짧은 문단과 목록을 섞어 필요한 정보를 찾기 쉽게 배치한다.
- 기존 표와 같은 내용은 다시 나열하지 않고, 회의에서 추가되거나 달라진 정보와 논의된 쟁점을 기록한다.
- 사람 이름은 원문이나 회의 자료에서 확인한 표기를 유지한다. 사용자가 이름 표기 방식을 지정하면 그 기준을 따른다. 화자의 신원이나 이름을 추측하거나, 별도 요청 없이 소문자화·인라인 코드·태그·멘션으로 바꾸지 않는다.
- 확정 여부, 담당자, 날짜, 수치, 완료 상태를 임의로 보완하지 않는다. 목표 일정과 완료 사실, 제안과 합의, 검토와 구현을 구분한다.
- 전문 용어는 업무 맥락에 맞게 유지하고, 불참자에게 필요한 설명만 덧붙인다. 쉽게 쓰기 위해 사실이나 조건의 정확성을 낮추지 않는다.
- 중립적이고 자연스러운 한국어로 작성한다. 없는 감정, 평가, 인과관계, 중요도를 추가하지 않는다. 이모지는 사용하지 않는다.

## 6. 작성 예시

아래는 형식을 보여주는 가상 예시이며, 현재 회의의 사실로 사용하지 않는다. 요약 예시는 해당 구분만 발췌했다.

### 조건이 있는 결정

입력:

> QA에 통과하면 금요일에 배포합시다. 실패하면 배포는 보류하고 일정을 다시 정하죠. QA 결과는 민수가 목요일까지 확인해서 공유하는 걸로 합의했습니다.

요약:

```markdown
## 결정 사항
- QA 통과 시 금요일에 배포하고, 미통과 시 보류 후 일정을 재협의하기로 함.
- 민수는 목요일까지 QA 결과를 확인해 공유하기로 함.
```

### 반복 발언과 미결 안건

입력:

> 응답이 느린 건 외부 API를 여러 번 호출해서인 것 같아요. 같은 API를 반복해서 부르는 게 원인 같다는 얘기입니다. 캐시를 쓰거나 호출 횟수를 줄이는 방법이 있겠네요. 다만 개인화 응답을 어디까지 캐시로 공유할 수 있는지는 아직 모릅니다. 어느 방법을 쓸지는 결정하지 않았고 호출 로그를 더 볼 필요가 있습니다. 담당자와 기한은 정하지 않았습니다.

요약:

```markdown
## 논의 사항
### 응답 지연
- 외부 API 반복 호출이 원인으로 추정되며, 캐시 적용과 호출 횟수 축소가 대안으로 제안됨.
- 개인화 응답의 캐시 공유 범위는 미확인이며, 적용할 방법은 미결임.
- 호출 로그를 추가 확인할 필요가 있으나 담당자와 기한은 미정임.
```

## 7. Notion 배치와 검증

- 새 요약은 페이지 하단에 구분선과 '요약본' 토글을 추가해 배치한다. 저장 대상은 요약본이며, 원문을 새로 복사해 넣지 않는다.
- 비교용 버전을 요청하면 기존 요약본을 남기고 '요약본 v2'처럼 별도 토글로 추가한다. 특정 버전의 수정을 요청하면 그 버전만 수정한다.
- 요약 작성 규칙이나 참고 링크를 회의록 본문에 임의로 추가하지 않는다.
- 기존 본문, 표, 하위 페이지, 원본 전사, 요청하지 않은 요약 버전을 보존한다.
- 저장 후 요청한 구성과 순서, 토글 내부의 중첩, 이름 표기, 확정 여부와 작성한 요약의 내용이 누락 없이 저장됐는지 확인한다.
